## 0. 结论

1. **F4 修复成立（hub lane）**：`^C` / `^D` / `job_kill` 都只作用于对端命令，会话在同一个 shell 里存活；c 轮「整条会话死」不再出现。实测覆盖裸 `^C`、`^D` 两步 EOF、运行中 `job_kill`、超时 handoff 后 `job_kill`。
2. **F2 修复成立**：裸 `^C` 后 `job_kill` 连跑 3 次，3/3 干净结算 `killed · interrupted: exit 130`，无 `'rintf' not found`，无 reconnect；同会话后续命令正常。
3. **CF 成立**：对运行中的 hub job 执行 `close force:true`，job 结算 `killed · interrupted: exit 130`（非 `failed / session died`）；已关闭会话再 `input` 得到 `[E_NO_SESSION]`，4999 保持 `root=200`。
4. **F3 边界如实披露**：安装态含 `stdin.on('error')` 常驻监听；本轮没有稳定复现「异步 EPIPE」这一理论竞态，只验证了 force-close / 对端被杀后 4999 不崩。日志中唯一的 fatal EPIPE 是 **2026-10-19** 的旧 `super-dsh/remote` closure 栈，不是本轮。
5. **Surface 落地**：本会话工具描述即安装态 surface，含 Actions / Targets / PTY / Oneshot / Examples；PTY 四词导语与两个 Examples 逐字在列。`add {spawn}` 创建回执恰为 `[session created …]` + 标记行两行，**不再叠加 registered notice**；`status` 会话卡与 ledger、`E_LABEL_IN_USE` 均按 surface 工作。
6. **ssh / docker 无回归**：ssh PTY 的 `^C` + `job_kill` 仍为 `killed · exit 130` 且会话存活；docker PTY 的交互 `input`（`hi\n` → `GOT:hi`）正常。
7. **dev3 目标机已装 0.3.2-d**：4998 `root=200`，better/super 均 `0.3.2-d`，安装态 `plugin.js` 哈希与 PC 一致。
8. **测试账**：d 相关 5 个 spec **79/79 pass**；superd-hub `exec-pty.test.mjs` **8/8 pass**（含 F4 四条 lane 级钉）。完整 `test/remote` 在**本会话的 bwrap 沙箱 shell** 下为 **240 pass / 5 fail / 8 skip**；5 个失败全部是依赖本地 sshd fixture 的用例（`Connection to 127.0.0.1 closed by remote host`），与 d 改动文件无关（见 §6）。
9. **证据链一处记录错误（非产品问题）**：d 报告记录 better-dsh tarball SHA-256 为 `97f21dd4…`，实测与 `pair.json` 均为 `3c8868e4…`；三处 `plugin.js` 哈希链一致。建议修正旧报告记录。

## 2. F4 / F1 / F2（hub lane，`pty:pty-cqeb` / `hub:bfwu`）

### 2.1 运行中 `job_kill`（无先前 `^C`）

| 步 | 调用 | 回执（关键原文） |

| 2 | `job_kill remote-a22e1c55cd454da2` | `requested cancellation …` |

### 2.2 裸 `^C` → 会话存活 → `job_kill` 干净结算（F2 ×3）

每次都是：`sleep 120`（background）→ `input` 原始 `0x03`（回执 `wrote 1 byte`）→ `job_output` 仍 `[status: running]`（F1 如实，不误结算）→ `job_kill` → `[status: killed, interrupted: exit 130]`。

| 轮 | 命令 job | 裸 `^C` 后 | `job_kill` 后 | 同会话验证 |
| --- | --- | --- | --- | --- |
| 1 | `remote-79354c2657294f59` | `[status: running]`；随后 `exec` 得 `[E_SESSION_BUSY] … still runs a command (remote-79354c2657294f59) …` | `[status: killed, interrupted: exit 130]`（输出含 `^C`） | `pwd && echo ALIVE-CTRL-C` → `/tmp` / `ALIVE-CTRL-C`；标记行 `conn hub:bfwu · cmd remote-bef3e30ac898480f · cwd /tmp · exit 0 · 0.1s`，无 reconnect |
| 2 | `remote-4042306715cf4530` | `[status: running]` | `[status: killed, interrupted: exit 130]` | 继续复用同会话 |
| 3 | `remote-acfa3ca2684449d2` | `[status: running]` | `[status: killed, interrupted: exit 130]` | `echo ALIVE-3X` → `ALIVE-3X` |

`E_SESSION_BUSY` 的出现本身是关键证据：裸 `^C` 后本地会话仍活、对端 shell 已回提示符；旧 0.3.2-c 在同样一步会 `session died`，下一次 dispatch 只能重连到新 shell。

## 3. CF / F3

### 3.1 `close force:true`（运行中的 live job）

| 步 | 调用 | 回执 |
| --- | --- | --- |
| 1 | `exec target:"hub:bfwu:pty:d4cf" cmd:"cd /tmp && sleep 300" run_in_background:true` | `Started remote-52ee581f1c6a46b7 on pty:pty-9weg (d4cf) (hub:bfwu).` |
| 2 | `job_output` | `[status: running]` |
| 3 | `close target:"pty:pty-9weg" force:true` | `closed pty:pty-9weg (hub:bfwu) — killed running job remote-52ee581f1c6a46b7` |
| 4 | `job_output` | `[status: killed, interrupted: exit 130]` |
| 5 | `input target:"pty:pty-9weg" stdin:"x\n"` | `[E_NO_SESSION] remote: no live PTY under id pty-9weg …` |
| 6 | `curl 127.0.0.1:4999/` | `root=200`；`/api/session` 匿名 `401` |

结论：CF 目标达成——force close 的 job 结算 killed 族，不是 `failed / session died`；4999 不崩。

### 3.2 F3：边界与如实披露

- 安装态确认 `stdin.on('error')` 监听存在（`stdin write failed` 字符串 ×1）；代码上异步 EPIPE 只记 diag，死亡语义仍由 `proc.close → markDead` 独占。
- **直接复现未成功**：F3 原本就是理论竞态（写已死 stdin）。本轮尝试了更接近真实故障的路径：在 hub PTY 内取对端 shell PID，用 `hub:bfwu` oneshot `kill -9` 杀掉它，随即 `close force:true`。结果 job 结算为 `[status: failed, session died]`（对端会话确实先死，属诚实语义，不是 CF 的 live-force-close 路径），4999 仍 `root=200`；没有新的进程级 uncaught。
- 日志复核：`.scratch/superd-4999.log` 中唯一的 `dsh: fatal uncaught exception: Error: write EPIPE` 位于 **2026-10-19** 的启动段（栈为旧 `super-dsh/remote/plugin.js` 的 `PtySession.dispose`），在本轮启动（`token=tqNjo…`）之前多个重启周期；本轮无新增 fatal。
- 因此本报告把 F3 记为 **「安装态 guard 存在 + force-close/对端死亡不崩」**，不宣称已复现并验证异步 EPIPE 本身；若发布记录要求 F3 行为级证据，需另造可注入的 stdin 故障夹具。

## 4. Surface（安装态即模型所见）

本会话的 `remote` 工具描述直接来自安装态，逐段核对：

- **Actions**：`exec` / `add` / `status` / `input` / `close`，`action` 唯一派发；`unknown fields are rejected`。
- **Targets**：`<machine>:pty[:label]` = 新建；`pty:<id|label>` / bare label = 复用；前缀强制通道；`E_LABEL_IN_USE` 提示。
- **PTY 四词导语**：`stateful oneshot, interact-able stdin, managed output, persistent env`；含 `Read: job_output(jobId). Cancel: job_kill; try Ctrl-C first.`、`exec.stdin = startup input; input = subsequent input.`、`input is verbatim …`、`Input receipt confirms write only; read result via SAME job.`、`~30k chars per read`、`Idle expiry: 15 min`。
- **Oneshot**：stdout/stderr 分离、exit verbatim、startup-only stdin、`superd-run` / POSIX shim / `hub-lease` 三态、`scriptPath`、`The endpoint needs bash only — no Python.`。
- **Examples**：BYO-PTY 一跳登录（含两行创建回执与 `conn BYOP` 标记、managed output、background job + `job_output`）与 BYO-SSH 注册一次到处用（`remote_transfer {mode:"rsync", src:"ssh:lab:/var/log/app/", dst:"/home/u1/app-logs/", argv:["-a"]}`，绝对端点）。
- **Hub 附录**：`hub:<m4>` 的选择、`hub-lease` 披露、`4096` inline、`hub:<m4>:pty[:label]` 同形会话。

行为核对：

1. `add {spawn:"bash --noprofile --norc -i", target:"pty:d4byo"}` 回执**恰为两行**：`[session created — address it as pty:pty-d6ni]` + `[pty:pty-d6ni (d4byo) (byo-pty) · conn BYOP · idle-left ~15m · exit null · 0.0s]`；无 `registered — …` notice（T3 微调成立）。
2. 该 BYO 会话 `exec "echo BYO-OK && hostname"` → `BYO-OK` / `homepc`；`status {target:"pty:pty-d6ni"}` 返回会话卡 + ledger（`remote-267bf7d25c3246fe · exit 0 · 0.0s · echo BYO-OK && hostname`）。
3. 复用已占用 label：`docker:corti:pty:d4dock` → `[E_LABEL_IN_USE] … To address it / To free it / To create new`，与 surface 的 target 规则一致。
4. 两个 Examples 的 add/exec 动词、`remote_transfer` 的 `mode`、绝对路径均与现行代码一致；安装态描述中没有 `remote {action:"rsync"}` 之类的旧形状。
5. `docs/remote-tools.md`（与 better-dsh 副本同文件）保留 d 语义：`Cancelling is reliable (0.3.2-d)`、raw half 与 `killed · exit 130`、`session closed` 边界。该文件是长文人类文档，不是模型 surface，故不要求逐字同文。

共同形态：`sshd fixture startup` 能监听，但客户端 `ssh` 得到 `Connection to 127.0.0.1 closed by remote host` / scp exit 255。本会话的 bash 运行在 `bwrap --ro-bind / / --unshare-pid --tmpfs /tmp` 沙箱内；该环境下 fixture 的 sshd 能监听但无法接纳会话（具体沙箱限制未进一步定位，`/run/sshd` 对当前用户不可写只是相关线索）。这是**测试夹具环境问题**，不是 d 代码回归（d 相关 spec 与 hub lane 全绿）。d 报告记录的 245/0 是另一条（未受此沙箱限制的）运行线。
