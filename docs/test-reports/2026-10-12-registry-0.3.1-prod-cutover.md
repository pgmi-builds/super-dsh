# Registry 0.3.1 cutover to production (PC + dev3)

Date: 2026-10-12 (Asia/Hong_Kong). Scope: install the **published npm-registry `0.3.1`** into the two **production** Super Dash instances and restart their services. Verdict: **complete and verified on both machines.**

Authorization: the user explicitly directed the registry install and the restart to "pc and dev3, both prod" (2026-10-12). Both production restarts were executed **inline** — no delayed or detached restart was used for production. (A detached restart was used earlier only for the PC *test* unit, because that unit hosts the agent session performing the work.)

Neither production profile has an `.npmrc`, so both installs resolved against the **real** `https://registry.npmjs.org/` (unlike the test lines, whose profiles point at their local verified-pair registries).

## Procedure

```
DSH_HOME=/home/u1/.dsh dsh plugin --profile web add super-dsh@0.3.1 better-dsh@0.3.1
```

Per machine, in one sequence so production never serves from a half-installed tree:
`backup package.json + pnpm-lock.yaml` → `systemctl --user stop dsh.service` → CLI registry install → `systemctl --user start dsh.service` → readiness poll.

Both packages were requested together: production already carried the synchronized pair at `0.3.0-g`, and pre-installing Better keeps the runtime's companion step a no-op (receipts below confirm).

## Errors and observations

1. **Readiness-predicate bug (test harness, PC).** The PC poll accepted the first non-`000` response and stopped on a transient **404** at 09:40:36, briefly suggesting a failed boot. Re-probing settled to **401** within seconds; the 404 is the documented pre-route-mount moment already observed on dev3 during the `0.3.0-s` round. The dev3 pass used a corrected predicate (accept only `200`/`401`, ignore `404`/`000`) and reported `readiness=ready tries=6`.
2. **First pass was mis-scoped.** Production was only touched after the user's clarification; the test-line installs were kept (they are the same published bytes and the lines are healthier for it), not reverted.
3. **Verification method.** Artifact identity is established by lockfile `integrity` equality with the live registry metadata plus installed `package.json` versions — not by whole-tree hashing of `node_modules`.
