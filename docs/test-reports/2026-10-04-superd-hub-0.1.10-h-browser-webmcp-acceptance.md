## Browser Use 与 WebMCP 的实际分工

两者都用了，且调用途径可以区分：

1. **Codex Harness Browser Use**：通过 `mcp__cua_repl` 绑定既有 tab；使用 `tab.playwright.getByRole(...).click()/fill()` 点击历史会话、模型菜单、Continue，输入 Lexical composer，发送部分 prompt；使用 `domSnapshot()` 读取完整页面。它提供浏览器访问通道。
2. **网站 WebMCP**：通过 `tab.capabilities.get("webmcp")` → `fetchTools()` → `tools.call(name, args)` 直接调用当前网站暴露的工具。本轮实际成功调用 `dev_snapshot`、`dev_click`、`dev_fill`、`dev_wait`、`dev_eval`、`dev_console`、`dev_network`。切换 runtime / 返回 DSH 多次使用 WebMCP `dev_click`；回复等待、页面文字、错误读取也使用 WebMCP。
3. 页面工具来自 dev-only `superd-dev-webmcp`，共 **22 tools**，页面角标为 `page-mcp · 22 tools · native WebMCP`。它们是浏览器操作/检查工具，不是业务级 `spawnForeignSession` 工具；本轮通过 UI 触发 Super D 实际会话路径。
4. WebMCP 工具名带 UUID，当前 document 的 UUID 与此前 turn 的工具通知不同。首次旧工具名调用失败后重新 fetch；不能把历史通知里的名称当成当前可调用名称。
5. Hub 异步刷新会替换按钮节点，导致旧 `eNN` ref 失效。后续基于已观察到的 `aria-label` 使用稳定 CSS，例如 `button[aria-label="Switch to DSH"]`。
6. `dev_fill` 曾报告成功写入 OMP Lexical textbox，但 Send 仍 disabled。改用 Browser Use 的角色定位 `fill()` 后 Send 启用并成功发送。该现象属于页面工具与 Lexical 的输入适配差异，不是 Foreign Agent 发消息失败。
7. Preview Notice 的 Continue 不涉及条款接受。新会话遇到该 modal 后先关闭，再等待 modal 移除才输入；一次过早 fill 触发 Browser Use clipboard target mismatch，重新观察页面并重试后恢复。

所有业务操作走 UI；未用 HTTP RPC 脚本代替新建、resume 或模型选择。`dev_eval` 只读取可见 DOM 文本、按钮 aria-label 与消息存在性，不调用隐藏业务接口。

## Findings 与复现

### F1 — Codex sessionController 不可用（阻断）

复现：Hub → Switch to Codex → New Session；或展开 Ungrouped → Untitled → Select model。分别得到 create、follow、modelCatalog 的 gateway/service-unavailable。影响 Codex 主路线完整会话面。不能以 Hub seat 或接口层 HTTP 200 判可用。

### F2 — 当前会话模型芯片 / 统计没有及时更新（四条路线）

复现：进入上述 Claude / Pi / Hermes / Antigravity 旧会话 → 模型菜单 → 选择另一个模型 → 菜单收起 → 等待至少 10s → 芯片仍旧 → 发 MODEL prompt → 收到新回复，芯片仍旧 → 切去其他 runtime 再回来并重新打开该旧会话 → 芯片显示新模型。

选择确实持久化，因此“后端完全不支持模型切换”不成立。缺陷确定在用户可见实时状态；真实调用的底层模型没有单独验明。Antigravity / Pi / Hermes 当前页 footer 也仍显示续聊前的 turns / token 统计，重开后恢复。尚未证明这些现象共享同一根因。

不含 HTTP 正文的 WebMCP 网络证据（时间为工具 UTC，可换算 +08:00）：

```text
[13:04:22.725] 200 POST http://127.0.0.1:4999/api/session/selectModel 15ms 167B
[13:07:19.240] 200 POST http://127.0.0.1:4999/api/session/selectModel 94ms 161B
```

这是工具 ring buffer 中保留的 Pi / Hermes 选择请求元数据，不作为模型执行证明。

### F3 — Hermes 本轮用户 prompt 未完整重放

复现：在旧 `UI-OK-ZAI` 会话发送 RESUME 探针 → 选择 glm-5-turbo → 发送 MODEL 探针 → 两次都有独立 Completed 回复 → 离开后重开该旧会话。RESUME user + assistant 可见，MODEL assistant 可见，但 MODEL user prompt 不在 DOM。即时视图曾出现 assistant 在该 user prompt 前面的顺序异常。

只确认 UI / replay 缺项，没有读取底层会话正文来推断磁盘是否丢失，因此不能直接判为存储丢数据。此项影响“session log transcript 完整重放”的验收。

## 验证边界与交接

- 本轮是当前本机 4999 交付形态的第一人称 UI 验收；没有 dev3 实装、WAN/LAN 或全矩阵 provider 探针，不能充当发布放行。
- 新建五个测试会话；五个既有测试会话各追加 RESUME 和 MODEL 探针。没有删除历史测试资产。
- 真实 resume 指 UI 打开旧会话并续聊成功；不包含停掉实例 / 清空子进程后的 cold resume 验收。
- 生成只要求固定文本并禁止 tools / 文件修改；没有验收 runtime 的工具执行、审批、steer 等扩展能力。
- 每条路线结束后切回 DSH Native，观察 Standard mode / Workspace Write / DeepSeek-V41-Flash / High，Native composer 正常。OMP / Antigravity / Claude / Pi / Hermes 各阶段 console error 检查为空；Codex 已记录的错误不归入 Native 回切失败。
- 一次 WebMCP `dev_network(include_bodies:true)` 被自动审批拒绝：可能暴露敏感会话或凭据相关数据。没有读取正文或通过替代接口绕过；随后只读取 `include_bodies:false` 网络元数据，且成功。本报告依赖 DOM 可见证据，不依赖被拒绝的正文检查。
- 遗留：优先修复 F1；排查 F2 当前会话投影更新；排查 F3 Hermes 消息顺序与 user entry 重放。修复后在整包线上重跑相同 UI 探针。
