## 七、补录（2026-09-24 同日）：世界页 Reconnecting 根因与修复（0.1.3-j → 0.1.3-l）

### 现象与误诊纠正

user 报「切到任何 foreign agent：空白 + 永远 Reconnecting（6/6）」。初诊「`/<label>/api/remote.mux` upgrade 挂起」是**探针伪影**：curl 收到 101 后等连接关闭才退出（curl 不讲 WS），ctx0 mux 的 ~5.7s 是上游心跳（2s ping、2 次 miss 即 terminate）杀无 pong socket；我们的 mux 心跳默认 30s → 6-8s 探针超时内既不关也不报。**任何 mux 探针必须用真 WS 客户端**（`ws` 包直连即可）。同法复测：升级握手 7-27ms、全双工 round-trip 健康——传输面从来没问题。

### 真根因（headless Chrome 复现 + WS 帧抓取）

headless 探针（playwright 驱动 `/usr/bin/google-chrome`）复现 user 症状后抓帧，看到服务器主动回错帧并反复被客户端放弃重连：

1. **0.1.7 流协议新增上行帧**：`RemoteStreamClientMessage` 增 `item`（上行项，`value` 可省）与 `end`（上行半关闭）。我们的 wire-compatible mux（`world-mux.ts`）只认 `open`/`cancel` → 0.1.7 客户端任一上行帧触发 `close(1008, 'invalid Remote stream request')` → connection lost → 重连 → 再错帧 → 永远 Reconnecting。
2. **carrier 的 world 网关调用参数错位**（0.1.3-j 移植时就错）：`openWireStream` 规范参数序 `(endpoint, payload, uplink, peer, signal, control)`，我们只传 3-4 个 → `signal=undefined` → `$events`/`workspace/follow` 服务端 `ERR_INVALID_ARG_TYPE: signals[0] … Received undefined` / `Cannot read properties of undefined (reading 'signal')`。

### 修复（0.1.3-k 试装、0.1.3-l 定版；0.1.3-k 为弃用中间版）

- `world-mux.ts` 全面对齐上游 `stream-protocol.ts` + `stream-server.ts`：4 类客户端帧解析（exactKeys 与上游一致）；`item`/`end`/`cancel` 对已出表 stream **静默丢弃**（上游语义）；duplicate `open` 仍 1008；`UplinkInbox` 有界单消费队列（字节上限，默认 256KiB 与上游同）——`end` 后 item / 溢出 → `gateway/protocol` / `gateway/uplink-overflow` 失败帧；downlink 落定后 inbox fail；abort 原因带 `code` 才回失败帧（取消静默）；心跳默认 30s → **2s**（上游对齐）。
- `carrier.ts`：`CarrierGatewayFace.openWireStream` 换规范 6 参签名，mux 适配器 `(endpoint, payload, uplink, control) → openWireStream(endpoint, payload, uplink, undefined, control.signal, control)`（= 上游 gateway 构造器同款接线，peer 无、以 ctx0 fence 为准）。
- 单测：world-mux 10 用例（新增：uplink 全量/无值项、end 半关闭、世界不读 uplink、settled 后迟到帧丢弃、item-after-end、溢出、duplicate open）；hub 全套 **89/89**。
- 另新增 carrier 的 `/<label>/open-in-app` 前缀桥（见遗留：世界自建 fence 仍 401）。

### 验证（交付形态）

- 副线复现线（4998 + 全新 home `.tests/aw2` + SUPERD_TRACE）：修复前 headless 复现 4 次 connection lost；修复后 1 条 WS **still-open**、`$events` ready 帧、`workspace/follow`/`session/control` 正常流基线与增量、**无** Reconnecting banner。复现线已拆除（unit 停 + home 删）。
- 正线 4999（0.1.3-l）：`world failed` 0；6 挂载 `POST /<label>/api/session/list` 全 **200**；headless 探 `/codex/`：console 干净、无 4xx/5xx、无重连、WS 常驻流帧正常。
- 探针方法论沉淀：真 WS 客户端探协议、playwright+chrome 探页面、`.credentials.yaml` 的 `client-connection/browser-session` secret 可铸造探针 cookie（authority 绑定名 + HMAC）。

### 遗留（新增）

- **世界页 open-in-app 401（先存问题，0.1.6 同形）**：世界自己的 open-in-app web 路由调用**世界自己的** `connection.requestRejection`（cookie 对世界树自己的 secret 验签）→ ctx0 cookie 401（裸 401、Content-Length 0）。属「单认证域」未贯彻到世界自建 web 路由；候选修法 = `provisionWorldProfile` 把父 home 的 browser-session secret 同步进世界 home（`initializeSecret` 只在记录缺失时生成，共享记录即共享 cookie 域）。非阻塞（console 噪音 + 世界页 open-in-app chip 降级）。
- HMR 全量 reload 后 launch token 轮换（`ctx.root` 换代）：已开浏览器凭 cookie 不受影响；换新浏览器需取新 token URL（本次 05:33 前后多次重启期间观察到的 401 即此）。

## 九、补录（同日）：foreign 会话跨重启不可恢复——v4 会话格式全面对齐（0.1.3-p）

### 现象与三层根因（全部是 0.1.7 v4 读者新增的校验）

user 报「重启后所有 foreign agent 会话不可恢复」。逐 log 验证（`session/page` 逐条打）定位三层：

1. **protected head 规则**：`system/message` 必须是 surface 首节点（成为 protected head）或替换既有 head——bridges 在首条 user 消息**之后**追加系统提示 → `system/message requires a protected first surface head`。
2. **step 上下文规则**（首诊漏掉的一层）：`system/message` 的 turn/step 必须匹配**当时打开的** turn+step——bridges 的 user 消息写在 turn 级（step 未开）、omp 的 bootstrap stamp 甚至在 turn 外 → `system/message does not match an open turn and step`。原生形状 = `turn/start → step/start → system head → user/message`。
3. **title 引用规则**：provider 来源的 `session/title` 的 `messageSeqs` 必须**非空**（引用其命名的 user 消息；空 seqs 仅限 user 来源）——hermes 镜像写空 seqs → `session/title messageSeqs must be empty exactly for a user title`。

### 写入侧修复（`agent-hub/src/system-head.ts`，withSystemHead v3）

一步 wrap（`this.session = withSystemHead(session, () => createSystemMessage(""))`）挂在六个 adapter 构造器上，透明 Proxy 按 v4 读者同款状态机跟踪 turn/step：
- 首条 `user/message` 且 surface 无 head：**代开 step**（turn 打开而 step 未开时）→ 占位 head（空 prompt，真实 prompt 稍后 **replace**——被替换的 head 出 derived model history，占位符永不达模型/UI）；
- adapter 自己的 `step/start` 若与 wrap 已开的 step 重复 → **丢弃**（log 已有，追加即重复）；wrap 开的 step 活到 `turn/end` → 先补 `step/end`；
- `stampSystemPrompt(turn, step, msg)`：append-or-replace head；无打开 step 时**排队**，在 adapter 下一个 step/start 里落地（omp bootstrap 场景）；headless 旧 surface 永不 stamp（保持合法而非制造腐坏）；
- adapter 直接 append 的 `system/message`（agy 通知）：无 step 则代开 + 坐标归一。
- claude 移植中发现并修复**重入缺陷**：`commitStepStart` 递归 `emitSystemMessage`，外层调用须在递归后**复查一次性 flag**（旧 snapshot guard 兼任此职，替换语义下必须显式）。
- hermes title 修复：镜像记录首个 user seq；无 user 消息时跳过镜像。

测试：hub `system-head.test.mjs` 9 用例**内置 v4 读者镜像校验器**（每条用例的事件流按读者规则复验）；全套 hub **106/106**，六 adapter 全绿（pi 56、codex 70、claude 140、hermes 126+skip、agy 32、omp 49）。

### 存量数据修复（`scripts/repair-session-heads.mjs`）
