### 2.1 Peer-side corroboration of the stop leg (arrived after the matrix was read)

The dev3 agent's own account of the stopped turn was delivered on `v8dt6l` afterwards, and it shows the
cross-machine `stop` is not a soft detach — it cancels an in-flight tool call **inside** the peer runtime:

> Step 1 exec issued exactly as specified: `{mode:"oneshot", timeoutSec:60, cmd:"sleep 40"}`. It did NOT
> complete. The tool returned `Error: tool call aborted` — an interruption signature, not a timeout (no
> `timedOut` flag, no stdout/stderr/exit payload, well under the 60 s budget). … the stopped turn emitted no
> hub message on this conversation — the abort is what the caller sees.

So on the 0.2.0 lane: the stop reached the peer service (`a2a.stop … stopped=true`), aborted the running turn
mid-`exec`, surfaced the interruption to the stopped agent as a bare abort (no fabricated result), and the
peer hub then emitted the `stopped-by-initiator` notice that reached this session — with the stopped agent
correctly withholding its completion token because the command never returned. Depth and honesty of the stop
path are therefore both confirmed from the far side, not just from my own receipt.

## 3. Findings

### A1 — No SuperD change is required for DSH 0.2.0-rc.2 (so far)
See §2: 12/12 surfaces green, including both reply forms and a live cross-machine stop with its settlement
notice. SuperD's declared peer range (`>=0.1.5-0 <0.3.0-0`, prerelease-inclusive) already admits
`0.2.0-rc.2`, and empirically the compatibility gate disabled **zero** SuperD rows.

### A2 — dev3's Codex world has no session plane — **pre-existing, not a 0.2.0 regression**
`bfwu-92tgxg` is the one agent whose `session/list` leg is dead on dev3 (`active Service "sessionController"
is unavailable`, 0 rows), and any A2A to it fails at `session/create` (line 12 of the matrix).
**This is not caused by the harness update.** The identical error was recorded **before** dev3's DSH was
upgraded: in the `0.1.8-e` round at **15:08** (dev3 then ran DSH `0.1.7-rc.1`, restarted 15:03:19) I captured
`agent_status bfwu-92tgxg → note:"collection failed for this agent — typert gateway: session/list: active
Service \"sessionController\" is unavailable"`; the DSH update landed at **15:15:53**, and the same failure
persists afterwards. On PC the same runtime is healthy (`c6uxel`, 5 rows).
dev3's boot shows `superd-codex: warning: 1 entry did not activate` + `session-controller … pending (waiting
for service: fileUploads)`; the hermes world shows the same warning pair but **works** (`dqsdy4`, 2 rows), so
the warning alone is not the discriminator. **Recommend** a dev3-local investigation of the codex world's
session-controller mount (it is a SuperD-world issue, but orthogonal to the 0.2.0 alignment).

### A3 — Third-party rows do break on 0.2.0-rc.2 (not SuperD)
dev3's journal carries `dsh: warning: 2 entries did not activate` with
`dashr-failover (better-dsh/failover): failed to import` and
`dashr-compaction-tuning (better-dsh/compaction-tuning): failed to import` (better-dsh `0.2.5`).
That is the "old plugin vs new harness" class the alignment question is about — it simply belongs to
**better-dsh**, not to SuperD. Worth forwarding to that line; it is the most visible 0.2.0 breakage on dev3.

### A4 — Methodology note for alignment probes: originate from a real session
A probe found on this rig at 15:22 (`cmp020`, messageId `a2a-compat-020rc2-…`) posted a `new-conversation`
envelope **directly at dev3's ingest** with a fabricated initiator (`session-compatprobe-0001-…`). dev3
happily adopted the mirror row and its agent replied — but the return path failed on the PC side with
`a2a.ingest.done kind=message outcome=failed` (`a2a/conversation-not-found`) and the reply was **buffered**
for the fake session. That is correct behaviour (no initiator row exists for a conversation this hub never
opened), not a defect — but alignment probes should be driven through the `send` tool from a real session so
the return path has a row. Directly-POSTed envelopes test only the ingest half.

### A5 — Environment: the rig is being tested concurrently
While this round ran, another session was using the same mesh: `exec` on dev3 writing
`SUPERD-EXEC-ON-020RC2-OK` (15:17:55), the `cmp020` probe (15:22), and at 15:31 an `exec` that read exactly
`xba6w9`/`v8dt6l` — my conversations — after which `v8dt6l.lastOutput` became
`"ALIGN-STOP-OBSERVED (dev3 leg · DSH 0.2.0-rc2)"`, i.e. a *different* tester drove the conversation I had
opened. The results above were each read immediately after their own call, but artifact attribution on this
rig should account for a second driver.

## 4. Verdict

**SuperD-to-SuperD across the harness generation gap is green: the mesh behaves the same when the peer sits
on DSH `0.2.0-rc.2` as when both ends sit on `0.1.7-rc.1`.** Roster federation, A2A in both directions
(including a peer-originated conversation), both reply forms, live cross-machine stop with its notice,
agent-status collection, exec and PTY all worked, and no SuperD row was rejected by the new harness's
compatibility gate. No SuperD-side change is indicated by anything observed here.

Two caveats keep this from being a blanket "0.2.0 is fully aligned": (i) the one broken runtime on dev3
(**Codex**) is an old, dev3-local failure that predates the update — it must not be attributed to 0.2.0;
(ii) the **client/UI half** was verified only statically (the page's boot payload references the SuperD
client modules) — no browser was available in this session, so Hub-UI rendering on 0.2.0 is unproven.
